# DXBerry-Pi — Console

Sub-project 3 of the DXBerry-Pi roadmap. Builds on the base image
(`docs/design/2026-09-07-base-image.md`, "the base spec") and radio plumbing
(`docs/design/2026-09-09-radio-plumbing.md`, "the plumbing spec"). Section
numbers in this document are its own.

## 1. Purpose

One web address that shows the whole station at a glance and does the
day-to-day jobs without SSH: see how the Pi, network, Graywolf, radios and
clock are doing; hand radios between applications; start, stop and read the
logs of services; open a terminal; change the Pi's own settings; and update
Graywolf, DXBerry and the system.

### Principles

- **A front door, not a cage.** Everything the console does stays doable over
  SSH with the same tools, and nothing the console installs takes a
  capability away.
- **Borrow the security-critical parts.** Login, sessions, request forgery
  protection, the terminal, service control and log reading come from
  [Cockpit](https://cockpit-project.org/) as packaged by Debian. DXBerry
  writes only the ham-radio page on top.
- **The CLI is the contract.** The page holds no logic of its own beyond
  display: every reading and every action is a DXBerry command with `--json`
  output and fixed exit codes, run through Cockpit. The logic lives in bash
  with the project's usual tests.
- **Same discipline as before.** Idempotent steps, atomic writes with
  read-back, `dxb_`-prefixed functions, bash 5 with awk and jq, tests without
  hardware, no version pins, no attribution lines of any kind.

## 2. Scope

**In scope (v0.3.0):**

- Cockpit installed and configured by a new setup step (§5, §12).
- The DXBerry page: status (§7), radio control (§8), services and power (§9),
  settings (§10), updates (§11).
- New commands `dxberry-status`, `dxberry-config`, `dxberry-update`.
- A DXBerry update file published with every GitHub release (§11.3).

**Out of scope:**

- Graywolf's own settings (station, beacon, iGate, digipeater) — edited in
  Graywolf's page, which the console links to (§10.1).
- Adopting radio channels made by hand in Graywolf (§8.3).
- Applications (sub-project 4), overlay-root, hotspot fallback, reverse
  proxy (sub-project 5).
- Signed releases (§11.3 notes the trust level).
- Remote access from outside the LAN.

## 3. User flow

1. Flash, fill in `dxberry.txt`, boot, as today. The status file on the boot
   partition gains a line: `console: https://10.0.0.90/ (log in as dietpi)`.
2. Browse to `http://10.0.0.90`; it redirects to `https://10.0.0.90`. The
   browser warns once about the self-signed certificate.
3. Log in as `dietpi` with the Pi's `PASSWORD`. The DXBerry page opens (§6.1).
4. The status cards refresh every 10 s while the page is open. Radios,
   services, settings and updates are one click away; Cockpit's own Overview,
   Services, Logs, Terminal and Accounts pages stay in the menu.

## 5. Access

### 5.1 Cockpit

`apt-get install -y --no-install-recommends cockpit-ws cockpit-bridge
cockpit-system`, the latest Debian version, never pinned. The
`--no-install-recommends` is required: the `cockpit` metapackage and the
packages' recommends pull NetworkManager and PackageKit, which would fight
`dxberry-netwatch` and ifupdown. Measured on Debian 13 (Cockpit 337): 19
packages, all libraries plus the three; Python 3 (the bridge) is already on
the image.

Cockpit is socket-activated: nothing runs until a browser connects. Measured
with one logged-in session: about 44 MB resident (`cockpit-tls`,
`cockpit-ws`, `cockpit-session`, the Python `cockpit-bridge`).

### 5.2 Login

The `dietpi` user with the Pi's `PASSWORD` (DietPi's global password sets it
at first boot). Root is refused by Cockpit's own
`/etc/cockpit/disallowed-users`. `dietpi` has password-free sudo on DietPi,
so Cockpit's administrative access works and the page runs every DXBerry
command with `superuser: "require"`. Cockpit's sessions, cookies and CSRF
tokens are used as they are.

### 5.3 Address

HTTPS on port 443 with Cockpit's self-signed certificate; port 80 redirects
to it; Cockpit's default port 9090 is dropped. One drop-in,
`/etc/systemd/system/cockpit.socket.d/dxberry-listen.conf`:

```
[Socket]
ListenStream=
ListenStream=443
ListenStream=80
```

`cockpit-tls` answers plain HTTP on any of its ports with a redirect to
HTTPS (`AllowUnencrypted` stays false); the redirect is expected to follow
the request's `Host`, landing on 443 — verified on hardware during the
build (§13). The certificate is Cockpit's own
(`/etc/cockpit/ws-certs.d/`), regenerated by Cockpit, never by DXBerry.

### 5.4 logind

DietPi masks `systemd-logind`. Without it Cockpit's own Restart and Shut down
fail ("Failed to schedule shutdown"), scheduled shutdowns fail, and PAM logs
a failed session on every login. `provision_console` unmasks it on every run
(a DietPi update could mask it again). It is static and pulled in by
`multi-user.target`, so unmasking is enough to have it at every boot.
Measured on the Pi: about 8 MB resident; a scheduled warn-only shutdown then
works and cancels, and Cockpit logins get real sessions.

## 6. The DXBerry page

### 6.1 Package

A Cockpit package: `/opt/dxberry/cockpit/dxberry`, linked as
`/usr/share/cockpit/dxberry`. `manifest.json` puts one entry, "DXBerry", at
the top of the menu (`"menu": {"index": {"label": "DXBerry", "order": -1}}`).
Cockpit opens the first entry of its ordered menu when the address has no page in it (checked in
Cockpit 337's shell), so DXBerry is the landing page.

Plain HTML, CSS and JavaScript loading `../base1/cockpit.js` — no build
tools, no framework, no files from outside the image. Temperatures are shown
in °F with °C beside them; the JSON carries Celsius.

### 6.2 How the page talks to the Pi

Every call is `cockpit.spawn([COMMAND, ..., "--json"], {superuser:
"require", err: "message"})`. Secrets (passwords typed into settings) go on
the spawned process's stdin, never in its arguments. The page shows the
command's own error text with the plain meaning of its exit code. Nothing on
the page reads or writes a file directly.

Long jobs (updates, applying settings) stream their output into the page and
can be left and come back to: they run as transient systemd units
(`systemd-run --unit=dxberry-job-…`), and the page follows the unit's journal.

## 7. Status

### 7.1 `dxberry-status --json`

One object; each part is collected independently, and a part that fails is
`{"ok": false, "error": "…"}` instead of failing the whole command (exit 0
whenever the JSON was produced).

| Part | Contents | Source |
|---|---|---|
| `pi` | model, CPU temperature (°C), throttling flags decoded (under-voltage now / since boot, frequency capped, throttled), load, RAM used/total, root disk used/total, uptime | `/sys/class/thermal`, `vcgencmd get_throttled`, `/proc` |
| `network` | state `ETH` / `WIFI` / `NONE`, address, gateway; on WiFi: SSID and signal | `dxberry-netwatch --status`, `ip`, `iw` |
| `graywolf` | service state, version, web URL, per channel: received, sent, bad FCS; iGate connected; position log on and its size | `systemctl`, `dpkg-query`, Graywolf API with the stored secret |
| `radios` | exactly what `dxberry-radio status --json` returns | plumbing spec §6.2 |
| `time` | synced or not, source (GPS, PPS, NTP), offset | `chronyc -c tracking`, `chronyc -c sources` |
| `release` | DXBerry, Graywolf and Cockpit versions; update badge from the cached check (§11.1) | `/etc/dxberry-release`, `dpkg-query` |
| `services` | the units of §9.1 with active / sub state and result | `systemctl show` |

The Graywolf part logs in with `/var/lib/dxberry/graywolf.secret`, as
`dxberry-radio` does.

### 7.2 On screen

Cards: Station (Graywolf, iGate, channels, position log), Radios, Network, Pi,
Time/GPS, About. Buttons: Open Graywolf, Graywolf log (§9.1), Restart
Graywolf, Restart / Shut down the Pi (§9.2).

## 8. Radio control

### 8.1 Known radios

From `dxberry-radio status --json`: name, label, parts (sound card, CAT
serial, PTT serial, HID), rig model, rigctld state and port, frequency and
mode, present or unplugged, owner, wiring. Per radio: **Give to Graywolf**
(`claim NAME graywolf`), **Release**, **Edit** (`set`), **Remove** (confirm;
releases first).

`dxberry-radio status --json` also carries `apps` (`[{name, label}]`, one per application module; a
module's optional `app_<app>_label` gives the label) so the page offers **Give to <label>** for every
application without knowing them in advance, and `warnings` (this run's warnings: `cockpit.spawn`
hands a command's stderr to the page only when it fails). **Give to**, **Release** and **Remove** say
first when an application stops because it owns no other radio (plumbing spec §9.2); giving a radio
to Graywolf while Graywolf has channels not named after a DXBerry radio says that those hand-made
channels may compete for the same sound card (§8.3). A radio's buttons are disabled while a change
to it runs, and `dxberry-radio` changes the record one command at a time (a lock; a second change
waits up to three minutes, then fails with exit 6); the change runs as a plain `cockpit.spawn`, which
survives moving between Cockpit's pages (closing the browser tab ends it, and clicking again finishes
an interrupted hand-over).

### 8.2 Plugged in, not set up

From `dxberry-radio scan --json`: each candidate with its functions and the
profile it matches. **Add** opens a form filled from the profile — name,
label, rig model (Hamlib's list from `rigctl -l`, searchable), PTT method and
type, baud, wiring — and runs `dxberry-radio add`.

`dxberry-radio status --json` carries `candidates`: the `scan` entries none of whose functions a
radio pins yet, so the page and `sudo dxberry-radio status` list them without matching pins
themselves. The rig models come from `dxberry-radio models --json` (`rigctl -l`, cut at its header's
columns because a name can be blank). The form passes each chosen function by its USB port path
(`--audio usb-0:1.3:1.0`), which `add` and `set` accept beside a scan index, so an interface plugged
in while the form is open cannot change what gets pinned; a path with nothing plugged in is exit 4.
**Edit** sends `set` only the fields that changed. The form is a dialog outside the cards, so the
10-second refresh never clears it.

Exit codes map to the plumbing spec's table (§6.2 there): 3 "no such radio",
4 "the device is not plugged in", 5 "the application could not take the
radio; it was left released", 6 "applying the change failed", 7 "the current
owner could not be re-wired".

### 8.3 Hand-made Graywolf channels

The console never adopts a channel made by hand in Graywolf. Giving a radio
to Graywolf creates DXBerry's own channel for it; a hand-made channel on the
same sound card would then compete with it. Switching a hand-configured Pi
over (remove the old channel, point digipeater rules and the beacon at the
new one) is a one-time operator job, not a console feature.

The page only warns. **Give to Graywolf** for a radio with full wiring names the hand-made channels
first, or says that Graywolf is not answering, so they could not be checked; a radio with names
wiring gets no Graywolf channel from DXBerry, so neither Give to nor Release mentions one. **Add**
notes under the sound card that pinning it renames its ALSA id to the radio's name in capitals at the
next replug or reboot, after which a hand-made channel on that card stops working.

## 9. Services, logs, terminal and power

### 9.1 Services card

Units: `graywolf`, every `rigctld@*`, `gpsd`, `chrony`, `dxberry-netwatch`,
`dxberry-radio-hotplug`, `dxberry-radio-wire`, `cockpit.socket`. State
(running / stopped / failed, last result for oneshots) comes from
`dxberry-status`; **Start / Stop / Restart** run `systemctl` through Cockpit.
Stopping `graywolf` or `dxberry-netwatch` asks first. Each unit has a **Log**
link into Cockpit's Logs page filtered to that unit
(`/system/logs/#/?prio=debug&service=UNIT`, the format Cockpit's own Services page uses).

Cockpit's own Services, Logs and Terminal pages are used as they are. The
Terminal logs in as `dietpi`; `sudo -i` gives root.

### 9.2 Power

**Restart** and **Shut down** on the page run `systemctl --no-block start
reboot.target` / `poweroff.target` after a confirmation and show "Pi
restarting, reconnecting…" or "Pi shutting down…". As the Pi goes down the
connection drops and Cockpit's own Disconnected screen takes over; the
operator reconnects from there and logs in again once the Pi is back. With
logind on (§5.4) Cockpit's own Restart works too.

## 10. Settings

### 10.1 What the console changes

Pi-level keys only: `STATIC_IP`, `GATEWAY`, `DNS`, `WIFI_SSID`,
`WIFI_PASSWORD`, `WIFI_COUNTRY`, `HOSTNAME`, `TIMEZONE`, `PASSWORD`,
`SSH_PUBKEY`, `GPS_DEVICE`, `GPS_BAUD`, `GPS_PPS`, `POSITION_LOG`,
`CONSOLE`.

`PASSWORD` is also the console login, and `CONSOLE=off` turns off the console
being used; the page says so before saving either. Graywolf's admin password
(`WEBUI_PASSWORD`) belongs to Graywolf's page like its other settings.

Station, beacon, iGate and digipeater values (`CALLSIGN`, `LATITUDE`,
`LONGITUDE`, `BEACON_*`, `IGATE_*`, `DIGIPEATER`) are changed in Graywolf's
own page, which the settings screen links to. `dxberry.txt` still seeds them
at first boot and on `--reseed`, as the base spec describes; the console
never runs `--reseed`, so it never overwrites edits made in Graywolf.

### 10.2 `dxberry-config`

`dxberry.txt` on the boot partition stays the single source of truth; the
console edits the same file a user edits on the card.

- `dxberry-config get --json` — every console key with its value; secrets as
  `"set"` / `"not set"`, never their values; `network_editable`, whether `set`
  takes network keys (§10.3).
- `dxberry-config set KEY=VALUE … [--stdin] --json` — secrets are read from stdin as
  `KEY=VALUE` lines, only with `--stdin` (so a caller that sends nothing never hangs), never from the arguments. Validates the resulting file with the
  base spec's validator; on success writes it atomically with read-back
  (FAT: temp file plus rename), keeps the previous file as
  `/var/lib/dxberry/dxberry.txt.prev` (0600), then runs `dxberry-provision`
  in run mode as a job (§6.2). The provisioner consumes and scrubs secrets
  exactly as today.
- A plain provisioner run does not reseed Graywolf, so the two keys that
  also live in Graywolf are pushed by `dxberry-config` itself, through the
  one seed function each already has: `POSITION_LOG` via
  `dxb_gw_seed_position_log`, `GPS_DEVICE` via `dxb_gw_seed_gps`. Never a
  whole `--reseed`.
- Exit codes: 0 done — for `set`, once the file is written and the settings
  job has started (or nothing changed); 1 not root; 2 usage (also a password
  given as an argument, a key the console does not change, a password the
  file's parser would change — a space at either end, or wrapped in double
  quotes — network and other keys mixed, and while network settings are off
  any network key); 4 not valid or no `dxberry.txt`, nothing written (the
  validator's messages on stderr); 5 busy: a settings job runs, a network
  change waits to be kept or undone, or the settings lock was not free within
  30 seconds; 6 the settings could not be checked or written, or the snapshot,
  undo timer or job could not be started (rolled back), or `revert` found
  nothing to undo or could not restore; 8 the settings job's own exit when the
  provisioner or the Graywolf push reported failed steps — `set` never returns
  it, `dxberry-config job` reports it with the job's output.

`set` writes the file, then starts `dxberry-config apply` as a transient unit
(`dxberry-job-config-<time>`) and returns; `dxberry-config job --json` reports that job (running,
finished with its exit, or ended without one, and its journal lines), the undo's deadline, and
whether a restart is needed (`/run/reboot-required`, which `dxberry-provision` now writes when a
reboot is needed). `apply` runs the provisioner with `DXB_GW_UPGRADE=0`: a settings change never
upgrades Graywolf (§11.2 does). Exit code 5 (busy) is added: `set` refuses while a settings job runs
or a network change waits to be kept or undone, and also when `set`, `confirm` or `revert`
cannot acquire the settings lock within 30 seconds (another instance is running). Network settings
(`STATIC_IP`, `GATEWAY`, `DNS`, `WIFI_*`) are saved on their own, so the undo restores exactly
what changed; the page has separate Network and System dialogs.

### 10.3 Network safety net

In v0.3.0-rc3 the console does not change network settings
(`DXB_CONFIG_NETWORK=0`, the default): `set` refuses a network key with exit 2
and writes nothing, `get --json` reports `"network_editable": false`, and the
page shows the network values with a note (edit `dxberry.txt`, run
`sudo dxberry-provision`, restart the Pi) instead of the Network dialog. The
safety net below is built and tested but switched off, because restarting
`dxberry-netwatch` adopts an interface that is already up (base spec §8.4):
a change would not be tried before **Keep** commits it. A live re-apply —
cycle the interface, reconfigure WiFi, offer **Keep** only from the new
address, or apply through a trial boot — must be built and tested on hardware
first.

When any of `STATIC_IP`, `GATEWAY`, `DNS`, `WIFI_*` changed, `set` first
snapshots the network state the provisioner writes — the interfaces
drop-ins, DietPi's WiFi database and `dietpi-wifi.txt`, and `dxberry.txt` — into
`/var/lib/dxberry/network-snapshot/` (0700), then arms a transient timer
that runs `dxberry-config revert` (restore the snapshot, restart
`dxberry-netwatch`): ten minutes as a backstop while the settings job runs,
re-armed for two minutes once the provisioner has finished — the design
expected the network to change about three seconds later, when the
provisioner restarts `dxberry-netwatch`, which does not hold for an interface
that is already up (above). Each arm uses a new unit name
(`dxberry-config-revert-<ns>`) and stops the previous timer only once the new
one is armed. A transient timer does not survive a restart, so
`dxberry-config-boot.service` (installed by the console step whatever
`CONSOLE` says, ordered before `dxberry-netwatch` and after `/var/lib/dxberry`
is mounted) undoes a change still
waiting at boot. Restoring files rather than re-running the old config
matters: a replaced WiFi password was scrubbed from `dxberry.txt` and exists
only in the snapshot. The page then offers **Keep these settings**, which runs
`dxberry-config confirm` and disarms the timer; `confirm --json` answers
`{"ok": true, "kept": true}` when it kept a waiting change and `{"ok": true,
"kept": false}` when nothing was waiting (the change may already have been
undone). If the address changed, the page shows the new link; the confirmation
must come from the new address, which proves the Pi is reachable there. A lost
browser, a wrong gateway or a WiFi typo therefore undo themselves within two
minutes of being applied. An undo whose file restore fails is not recorded as
done — it is retried after 60 seconds.

## 11. Updates

### 11.1 `dxberry-update check --json`

Installed and latest versions of Graywolf (release `checksums.txt`, as the
base spec §9.1), DXBerry (GitHub releases, §11.3; what is installed is
`/opt/dxberry/VERSION`) and Debian packages (`apt-get -s upgrade` after
`apt-get update`), and whether a reboot is needed (`/run/reboot-required`).
Run when the page opens; the answer is cached in
`/var/lib/dxberry/update-check.json` for 6 hours, or 15 minutes when a part
of it could not be read (an offline Pi asks again soon). Nothing runs in
the background.

The check is `dxberry-update check [--refresh] --json`; it never runs inside
a job (it runs `apt-get update`), and each job drops the cached answer when
it finishes so the next check shows the new versions; a check that overlaps
a job is not cached. `dxberry-status`'s release part reports the cached
check in brief (`update: {graywolf, dxberry, system, checked_at}`, a part
that could not be read is null), which the About card shows as "update
available", "check failed" or "up to date".

### 11.2 Graywolf

`dxberry-update graywolf` — the install path of the base spec §9.1, then the
position-history drop-in is rebuilt from the new package's unit (closing the
"hand upgrade keeps the old command line" gap) and Graywolf restarted, only
if it was running (`systemctl try-restart`: an operator who stopped it keeps
it stopped). A `GRAYWOLF_VERSION` pin in `dxberry.txt` wins: the check
reports "pinned" and nothing is updated.

### 11.3 DXBerry

Every GitHub release gains `dxberry-pi-<version>.tar.gz` (the contents of
`/opt/dxberry`: `bin/`, `lib/`, `templates/`, `share/`, `cockpit/`) and its
`.sha256`, built by `release.yml` from the tagged tree. `dxberry-update
dxberry`:

1. finds the newest full release (pre-releases only with **Include
   pre-releases** on, stored in `/var/lib/dxberry/update.conf`);
2. downloads the file and its checksum; a mismatch stops everything;
3. unpacks to `/opt/dxberry.new`, moves `/opt/dxberry` to
   `/opt/dxberry.prev` (replacing an older one) and `/opt/dxberry.new` into
   place — two renames on one filesystem, after a `sync`, with TERM, INT
   and HUP ignored until both are done; the job runs from a temporary copy
   of itself, so replacing `/opt/dxberry` under it is safe;
4. updates `/etc/dxberry-release` and runs `dxberry-provision` in run mode as
   a job.

The update file carries `VERSION` and a `RELEASE` file (version, commit,
build date) from which `/etc/dxberry-release` is written; a tree without one
(the image's own) falls back to its `VERSION`. The update's provisioner run
keeps Graywolf's version (`DXB_GW_UPGRADE=0`); every `dxberry-*` command
except `dxberry-preboot` is linked into `/usr/local/sbin`. An update and a
settings change never run at the same time, and an update does not start
while a network change waits to be kept or undone (exit 5).

`dxberry-update rollback` swaps `/opt/dxberry.prev` back the same way and
re-runs the provisioner. The checksum proves the file arrived intact, not
who made it — the same trust as the Graywolf download. Signing is a later
option.

A power cut between the two renames leaves no `/opt/dxberry`;
`dxberry-netwatch`'s unit then moves `/opt/dxberry.prev` back into place
before it starts (`ExecStartPre`), so the Pi still comes up on the network.
If a release's own updater is broken, the way back is by hand:

```
sudo mv -T /opt/dxberry /opt/dxberry.bad &&
  sudo mv -T /opt/dxberry.prev /opt/dxberry && sudo dxberry-provision
```

then delete `/opt/dxberry.bad`.

### 11.4 System packages

`dxberry-update system` — `dpkg --configure -a` first (it finishes an
interrupted install), then `apt-get update` and
`apt-get -y --no-install-recommends upgrade`, non-interactive, as a job;
changed config files are kept (`--force-confdef --force-confold`). When a
kernel or firmware package was upgraded (`linux-image-*`, `raspi-firmware`,
`raspberrypi-kernel*`, `raspberrypi-bootloader*`, `firmware-*`), the job
writes `/run/reboot-required` and says a restart is needed. This also
updates Cockpit. DietPi's `dietpi-update` is interactive and stays a
Terminal job.

Every update job's output streams into the page and stays in the journal
under its unit name (RAM, like all logs) until the next reboot.

## 12. Provisioning integration

`provision_console`, run after Graywolf and the radio step:

0. Install and enable `dxberry-config-boot.service` (§10.3), whatever `CONSOLE` says.
1. `CONSOLE=off`: stop and disable `cockpit.socket` if present, remove the
   DXBerry package link, status line "console: off"; done.
2. Install the three Cockpit packages (§5.1) when missing; a failure is a
   failed step, never fatal to the rest of the run.
3. Unmask `systemd-logind` and start it (§5.4).
4. Write the listen drop-in (§5.3) and the package link (§6.1); on change,
   `daemon-reload` and restart `cockpit.socket`.
5. Status line: `console: https://<address>/ (log in as dietpi)`.

New key `CONSOLE` (`on` default / `off`), validated like the other on/off
keys and documented in `dxberry.txt.example`. The reserved `CONSOLE_`
prefix stays reserved.

Ports now used: 80 and 443 (console). Graywolf keeps 8080; 8081, 6080 and
7681 stay reserved; 9090 is no longer used.

## 13. Verified assumptions and open risks

Verified on the rc2 Pi (Debian 13, DietPi) on 2026-09-28/29:

- The minimal Cockpit install is 19 packages with no NetworkManager or
  PackageKit; the three package names and `--no-install-recommends` are
  enough.
- `dietpi` logs in (HTTP 200 from `/cockpit/login`); root is refused (403).
- Overview, Services, Logs and Terminal work in a browser (checked by the
  operator).
- systemd's D-Bus API is reachable as `dietpi`; D-Bus is installed and
  active on this image.
- With logind masked, Cockpit's scheduled shutdown fails; with logind
  unmasked it schedules and cancels, and logins get sessions.
- Cockpit 337 runs `shutdown --reboot|--poweroff WHEN MESSAGE` as superuser
  for its power menu.
- `ttyd` is not in Debian 13 — one reason the terminal comes from Cockpit.

Verified on the Pi with the console installed (2026-10-06):

- Writing `dxberry.txt` atomically works on the FAT boot partition: `dxb_write_if_changed`'s temp
  file and rename land and read back, and nothing is left behind (checked on the Pi with v0.3.0-rc3,
  together with a rejected `dxberry-config set`, which wrote nothing, and a no-change `set`, which
  started no job).
- Hamlib 4.6.2's `rigctl -l` lists 313 models in fixed-width columns under a header (`Rig #`, `Mfg`,
  `Model`, `Version`, `Status`, `Macro`); every row aligns with the header, and a name can be blank
  (FLRig).
- Cockpit 337's shell shows that the first entry of the ordered `menu` is the landing page
  (with no path in the URL), so `"order": -1` makes DXBerry the landing page.
- Cockpit's Services page links a unit's journal as `/system/logs/#/?prio=debug&service=UNIT`.
- Port 80 answers `301 Moved Permanently` with `Location: https://10.0.0.90/`, so the redirect lands
  on 443 (§5.3).
- `dietpi`'s sudo runs without a prompt (`sudo -n true` as `dietpi`), which `cockpit.spawn` with
  `superuser: "require"` relies on.
- `dxberry-status --json` reads every part on the Pi in about 0.7 s.
- A transient timer cannot be armed twice under one unit name; `systemctl stop NAME.timer` unloads
  it. A `--collect` service is gone as soon as it exits and `systemctl show` then misreports its
  exit, so the settings job writes its own result; `journalctl -u UNIT` keeps its output.
- Cockpit 337's spawn promise has `input(data)`, which sends data on stdin and closes it.
- `/boot/firmware` is vfat: a rename there works (the atomic write of `dxberry.txt`), `chmod` does not.
- The GitHub releases API answers from the Pi without a token; `dpkg --compare-versions` orders `0.3.0~rc4` before `0.3.0`.

To verify during the build:

- That the DXBerry page's `cockpit.spawn` calls with `superuser: "require"` run as root from a
  browser session (the operator's browser check).
- Whether the Raspberry Pi kernel packages create `/run/reboot-required`
  themselves (`dxberry-update system` writes it for them, §11.4).

Risks:

- A DietPi update might re-mask logind or change sudo for `dietpi`; the
  setup step re-asserts logind on every run, and a lost sudo shows as a
  permission error on the page.
- A future Cockpit release might change its package or menu format; the
  manifest declares the Cockpit version it needs.
- The update file's checksum does not authenticate its origin (§11.3).
- Restarting `dxberry-netwatch` does not apply a network change: on start it
  adopts whatever ifupdown already has up (base spec §8.4, `nw_startup`), and
  a WiFi credential change does not even change `wlan0.conf`, so netwatch is
  not restarted at all. The safety net (§10.3) would therefore offer **Keep**
  for settings that were never tried, which then take effect at the next
  restart — a headless lockout risk. v0.3.0-rc3 ships with network settings
  from the console switched off. The same holds for a plain
  `dxberry-provision` run: a network change in `dxberry.txt` takes effect at
  the next restart, not when netwatch restarts (the provisioner says so and
  writes `/run/reboot-required`).

## 14. Testing

- The new commands are tested like `dxberry-radio`: fake `systemctl`,
  `dpkg-query`, `apt-get`, `curl` and sysfs fixtures; every JSON field the
  page reads is asserted, so a change that would break the page fails a test.
- `provision_console`: install / skip / failure, `CONSOLE=off`, logind
  unmask, drop-in and link idempotence, restart only on change.
- `dxberry-config`: validation failure writes nothing, secrets never in
  argv or output, the revert timer armed only for network keys, confirm
  disarms it, `.prev` handling.
- `dxberry-update`: checksum mismatch stops, the two-rename swap and
  rollback, the pin, the pre-release switch, the cache.
- The page has no automated browser tests. Each console pre-release comes
  with a short checklist run in a browser on a Pi.

## 15. Build order and releases

Each step is its own implementation plan, reviewed, and published as a
pre-release:

1. **v0.3.0-rc1** — Cockpit, logind, address, the DXBerry page with status
   (§5–§7), services and power (§9).
2. **v0.3.0-rc2** — radio control (§8).
3. **v0.3.0-rc3** — settings for the Pi's system keys (§10.1–§10.2); network
   settings from the console wait for a tested live re-apply (§10.3).
4. **v0.3.0-rc4** — updates (§11), including the release update file.
5. **v0.3.0** — full release, with the owner's explicit OK.

## 16. Hooks for later sub-projects

- Applications (sub-project 4) add a card and their units to the services
  list; their web UIs (Pat 8081, noVNC 6080) get links on the Station card.
- `dxberry-status` parts are keyed objects, so new parts add fields without
  changing existing ones.
- Hotspot fallback (sub-project 5) reports through the `network` part.
